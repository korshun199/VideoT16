# VideoT16 — знания и порядок испытаний распознавания дронов

Этот файл фиксирует, что уже подготовлено для проверки готовых моделей на видео, какие результаты получены и как продолжать испытания без вмешательства в рабочий запуск VideoT16.

## Для чего создана испытательная система

Цель — быстро и наглядно проверять, распознаёт ли готовая модель гоночные квадрокоптеры в реальных сценах, в том числе маленькие и далёкие объекты. Это локальный инструмент исследований на ноутбуке, а не обучение модели и не управление дроном.

Испытательный контур отделён от рабочего:

1. Из исходного видео вручную выбираются несколько показательных кадров.
2. Несколько готовых ONNX-моделей получают одни и те же сохранённые кадры.
3. Для маленьких объектов дополнительно проверяется обработка увеличенных фрагментов кадра.
4. Сохраняются CSV с измерениями и изображения с рамками для визуальной проверки.

Контур не меняет `lcam`, рабочие настройки, Raspberry Pi, OSD, видеопередатчик и видеотракт. Никакая модель не переобучалась.

## Что находится в проекте

- `scripts/video_trials.py` — просмотр видео и ручной отбор кадров.
- `scripts/compare_video_trials.py` — запуск ONNX-моделей на сохранённых кадрах, сравнение полного кадра и (по флагу) фрагментов.
- `tests/test_video_frame_sampler.py` — проверки отбора кадров и журнала сессии.
- `tests/test_compare_video_trials.py` — проверки отчёта сравнения, разбиения кадра на фрагменты, возврата координат рамок и объединения дубликатов.
- `test_samples/video_trials/` — локальные видео, выбранные кадры и результаты. Каталог исключён из Git через `.gitignore`.
- `models/` — локальные файлы моделей. Модели и их происхождение следует проверять отдельно: многие файлы в этом каталоге не публикуются.

### Ручной сбор кадров

Запуск:

```bash
.venv/bin/python scripts/video_trials.py /путь/к/видео.mp4
```

Управление окном:

- `Пробел` — сохранить показанный кадр в исходном разрешении;
- `P` — пауза/продолжение;
- `N` — следующий кадр, пока видео на паузе;
- `Q` или `Esc` — выход.

Скрипт не копирует и не перекодирует весь ролик. При первом сохранении создаёт новую папку сессии, кладёт в неё PNG и `manifest.csv` с именем исходного видео, номером кадра, временем и размером изображения. Повторно выбранный номер кадра в рамках одной сессии не сохраняется второй раз.

### Сравнение моделей

Пример запуска двух кандидатов на одном каталоге кадров:

```bash
.venv/bin/python scripts/compare_video_trials.py test_samples/video_trials/AvatarG0001_20261021_170123 \
  --model models/anti_uav_fast_256_int8.onnx \
  --model models/anti_uav_fast_320_int8_pc.onnx \
  --tiles --tile-size 480 --tile-overlap 0.20 --threads 2
```

Размер входа каждой ONNX-модели читается из самого файла; он не подменяется общим размером из рабочего конфига. В обычном режиме проверяется целый кадр. С `--tiles` дополнительно проверяются перекрывающиеся фрагменты. Скрипт переводит координаты рамок из фрагментов обратно в исходный кадр и удаляет сильно перекрывающиеся дубли одного класса.

Каждый запуск создаёт новый каталог сравнения и не перезаписывает уже существующий. Внутри находятся `results.csv` и картинки-оверлеи с рамками. В отчёте записаны модель, режим, размер входа, задержка инференса, максимальная сырая уверенность, найденные рамки и их координаты, а также числа рамок выше порогов 10–60%.

`--tile-size` задаёт желаемый масштаб разбиения и число фрагментов, а не гарантирует квадратный фрагмент строго такого размера: границы распределяются по всему кадру, чтобы закрыть края и сохранить перекрытие. Если нужно сравнить разные значения параметра, запускай два отдельных теста с разными `--tile-size` и разными `--output-dir`: параметр общий для всех моделей одного запуска.

## Набор испытаний 21 октября 2026 года

Исходный ролик — локальный `AvatarG0001.mp4`. Для экономии времени и вычислений кадры отбирались вручную, а не обрабатывался весь фильм. Каталог `AvatarG0001_20261021_170123` является ссылкой на `test_samples/video_trials/AvatarG0001_20261021_170123`.

Проверено:

- 104 выбранных PNG-кадра, нумерация выборки `sample_0038`–`sample_0141`;
- исходный размер изображений — 1280×720;
- 11 локально доступных файлов моделей сначала проверены на полном кадре;
- пять вариантов Anti-UAV дополнительно проверены на перекрывающихся фрагментах;
- картинки с рамками проверены визуально на характерных кадрах.

Данные не размечены как ground truth. Поэтому числа ниже — не точность, не полнота и не mAP. «Кадры с рамкой ≥70%» означает только число изображений, на которых эта модель выдала хотя бы одну рамку с такой уверенностью. Ложные срабатывания могут увеличивать этот показатель.

На этом наборе меньшие фрагменты чаще показывали маленький дрон, но требовали больше вычислений. У PC-варианта 320/480 были и ложные срабатывания на конструкциях крыши. `anti_uav_fast_256_int8.onnx` с фрагментами 480 px выглядит полезным кандидатом для следующего визуального A/B, но пока не объявляется победителем.

Эти времена измерены офлайн на CPU ноутбука в текущем окружении. Они не равны задержке камеры целиком, не предсказывают скорость Raspberry Pi и не подтверждают пригодность для пилотирования.

## Чему научились на испытании

1. Один только процент уверенности не говорит, что объект распознан правильно. Нужно смотреть, куда поставлена рамка, и учитывать ложные срабатывания.
2. Целый кадр уменьшает маленький квадрокоптер до малого числа пикселей. Разбиение на фрагменты увеличивает его для детектора и может вернуть часть пропусков.
3. Увеличение чувствительности имеет цену: несколько инференсов на исходный кадр повышают задержку и могут усилить ложные срабатывания.
4. Модель с большим числом рамок не обязательно лучше: пример `anti_uav_yolov8s_new.pt` показывает много уверенных попаданий по фермам ангара.
5. Сравнивать нужно на одинаковых кадрах, при явно записанных пороге, размере модели и размере фрагментов. Иначе разница может быть вызвана не моделью.
6. Короткая ручная выборка полезна для отсева моделей и диагностики, но окончательная оценка требует кадров с разными расстояниями, размерами цели, фонами и отрицательными сценами.

## Следующий этап

Следующий разумный шаг — небольшое визуальное сравнение двух кандидатов на тех же кадрах, а затем отдельная проверка на живом видеопотоке. Для сравнения на сохранённых кадрах:

1. Открывать пары оверлеев одного и того же `frame_file` рядом.
2. Сначала проверить, действительно ли рамка охватывает квадрокоптер, особенно на дальних кадрах; отдельно записывать рамки по фону.
3. Сравнить `anti_uav_fast_256_int8.onnx` с фрагментами 480 px и `anti_uav_fast_320_int8_pc.onnx` с фрагментами 640 px — это два измеренных компромисса, а не окончательная конфигурация.
4. Только после выбора кандидата проверять камеру и плавность работы в отдельном тестовом просмотрщике. Старый рабочий запуск и настройки не менять.

Полноценное окно для живого A/B-сравнения в рамках этих работ ещё не создано. Измерения на выбранных кадрах не доказывают время появления/исчезновения рамки при движении. Это отдельный следующий этап.

## Что сохранять и что не публиковать

В Git можно хранить исходный код тестовых инструментов, unit-тесты и этот документ. Не добавлять без отдельного решения владельца:

- исходные видео, выбранные кадры и другие пользовательские материалы;
- CSV-результаты, контактные листы и изображения с предсказаниями;
- веса моделей `.pt`/`.onnx`, если их публикация отдельно не согласована;
- журналы, персональные данные, ключи, секреты и конфигурации устройств.

На текущий момент `test_samples/` исключён из Git. Значит, отчёты и конкретный набор кадров доступны на этой рабочей станции, но не появятся после обычного клонирования репозитория. Для повторения опыта нужны тот же локальный набор кадров и те же файлы моделей.

## Проверенный живой профиль «небо» — 22 октября 2026 года

По просьбе владельца отдельно сохранены параметры камеры и модели, которые он визуально проверил на летящем дроне на фоне неба. Профиль хранится в `config/live_drone_profiles.json`; он не меняет `config/runtime_settings.json` и не подменяет обычный производственный запуск.

Из корня проекта запустить профиль можно одной командой:

```bash
./lcam
```

`lcam` находит корень проекта относительно своего расположения, поэтому для команды не нужно переходить в другой каталог. Он запускает тестовый просмотрщик `scripts/live_drone_trial.py` с профилем `sky`; параметры, журнал и ошибки показываются в консоли и сохраняются в отдельный файл под `test_samples/video_trials/logs/`. При нескольких камерах программа попросит выбрать источник. В тестовом окне `R` включает/выключает распознавание, `Q` или `Esc` закрывает окно и освобождает камеру.

Для прежнего обычного запуска системы используется `./lcam --production`; он по-прежнему читает настройки из `config/runtime_settings.json` и запускает `cam`.

В профиле `sky` зафиксированы: `source=auto`, модель `models/anti_uav_fast_320_int8_pc.onnx`, порог рамки 40%, нижний диагностический порог 5%, фрагменты 640 px с перекрытием 20%, два потока ONNX Runtime, без обработки полного кадра. Параметры воспроизводят последний журнал `live_drone_trial_20261022_094926_667364.log`: 478 измерений инференса, 333 кадра с рамкой выше 40%, средняя задержка инференса 91 мс (медиана 86 мс). В том запуске камера `/dev/video4` отдавала кадры 640×480 и сообщала 30 FPS. Владелец подтвердил изображение глазами.

Это сохранённый удачный полевой профиль, а не доказательство точности для любых условий. Показатель «333 кадра с рамкой» не является метрикой точности: эти кадры отдельно не размечались как эталон.

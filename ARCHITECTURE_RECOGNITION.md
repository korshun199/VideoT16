# VideoT16 — архитектура нового конвейера распознавания

Дата ревизии: 26 октября 2026 года.

Этот документ описывает именно настольный контур распознавания с USB-видеозахватом. Он не меняет Raspberry Pi, UART, OSD, J7, видеопередатчик или настройки внешнего оборудования.

## 1. Что сейчас есть в проекте

В проекте существуют три независимых контура, которые нельзя смешивать:

| Контур | Точка запуска | Конфигурация | Назначение |
|---|---|---|---|
| Рабочая система с Raspberry/OSD | `cam`, `src/local_object_detection.py` | `config/runtime_settings.json` | Базовый производственный код, включая выводы и телеметрию. |
| Настольное живое испытание V2 | `lcam`, `scripts/live_pipeline_trial.py` | `config/live_drone_profiles.json`, профиль `sky` | Поток с номерами кадров, отдельным потоком YOLO и диагностической вставкой обработанного кадра. `lcam --m` открывает меню этого профиля. |
| Старое живое испытание | `scripts/live_drone_trial.py` | `config/live_drone_profiles.json` | Исходный стенд и контроль для сравнения; запускается напрямую для диагностики. |
| Эксперимент движения | `lcam3`, `scripts/motion_trial.py` | `config/motion_trial.json` | Изолированный опыт: компенсация движения фона и кандидаты. Он не является рабочим распознавателем. |

Для перестройки используется только второй контур. Первый не переписывается и не запускается во время этой работы. Третий остаётся материалом исследования: его алгоритм нельзя включать в рабочий путь, пока он не пройдет отдельную проверку.

## 2. Установленная причина задержки

### Фактические измерения

На этой машине: Intel Core i5-1335U, 12 логических CPU, 15 ГиБ RAM. Журналы `lcam` от 26 октября показывают:

- окно держит примерно 41–43 FPS;
- полный обход четырёх фрагментов занимает примерно 650–1130 мс;
- быстрая проверка одного кандидата занимает примерно 160–500 мс;
- записанный возраст результата доходил до 2208 мс.

Следовательно, плавное видео и медленная нейросеть могут работать одновременно, но кадр с рамкой нельзя считать текущим кадром.

### Корневая ошибка данных

Сейчас `LatestFrameCapture` отдаёт только массив изображения. У него нет номера кадра, времени захвата и неизменяемого пакета кадра. `LatestInferenceWorker` возвращает только рамки и время окончания. Поэтому главный цикл делает следующее:

1. отображает самый свежий кадр камеры;
2. получает рамки от нейросети для более старого кадра;
3. рисует эти старые координаты на новом кадре.

Из-за этого рамка закономерно оказывается там, где объект был раньше. Функция, ограничивающая возраст результата, способна только скрыть старую рамку; правильно перенести её на новый объект она не может.

В двухступенчатом эксперименте есть и второй вариант этой же ошибки: `MotionResult` создан для одного кадра, а его координаты кандидата могут быть применены при вырезании участка из следующего кадра. Это делает неверным уже сам вход YOLO.

Та же архитектурная проблема есть в старом `src/local_object_detection.py`: фоновые рамки без идентификатора исходного кадра рисуются поверх очередного свежего кадра. Этот контур пока не трогаем, но его нельзя брать как основу новой реализации.

## 3. Чего не исправит увеличение числа потоков

Четыре фрагмента сейчас вызываются последовательно через одну ONNX-сессию. Параметр `threads` задаёт внутренние потоки ONNX Runtime, а не четыре независимых распознавания. Простое создание нескольких Python-потоков с несколькими сессиями может ухудшить результат из-за конкуренции за CPU и память.

Многопоточность нужна не для рисования старой рамки быстрее, а для правильного разделения ролей:

- чтение USB-потока не ждёт нейросеть;
- вывод на экран не ждёт нейросеть;
- тяжёлый инференс не накапливает очередь старых кадров;
- сопровождение обновляет координаты между редкими результатами YOLO;
- журналирование не участвует в критическом пути кадра.

## 4. Целевая одно-процессная многопоточная схема

Сначала используется **один процесс** и несколько специализированных потоков. Так проще передавать кадры без сериализации, проще остановка и меньше копий памяти.

```text
USB VideoCapture
      │
      ▼
[поток захвата]
  FramePacket(seq, captured_at, bgr, gray_small)
      │                    │
      │                    ├──────────────► [поток отображения]
      │                    │                   показывает только свежий кадр
      ▼                    │                   + OverlayPacket того же seq
[mailbox YOLO: 1 слот]     │
  старый ожидающий кадр     │
  заменяется свежим         │
      │                     │
      ▼                     │
[поток инференса: 1 ONNX-сессия]
  DetectionResult(source_seq, source_time, boxes, timings)
      │
      ▼
[поток сопровождения]
  проходит от source_seq до текущего seq
  по уменьшенным серым кадрам из кольцевого буфера
      │
      ▼
  OverlayPacket(frame_seq, boxes, verified_source_seq, tracking_age)
      │
      └────────────────────► [поток отображения]

[низкоприоритетный поток телеметрии и журнала]
  агрегирует цифры; не пишет строку на каждом кадре
```

### Пакеты, без которых схема не запускается

```text
FramePacket:
  sequence             целый строго возрастающий номер
  captured_at_ns       время получения кадра
  bgr                  исходный кадр, который никто не изменяет
  tracking_gray        уменьшенная серая копия для сопровождения

DetectionResult:
  source_sequence      номер именно того кадра, который видела YOLO
  captured_at_ns
  started_at_ns / finished_at_ns
  boxes                рамки в координатах source-кадра
  raw_confidence
  mode                 full_scan или tracked_roi

OverlayPacket:
  frame_sequence       номер кадра, поверх которого разрешено рисовать рамку
  boxes
  origin_sequence      исходный проверенный YOLO кадр
  status               verified, tracked или expired
```

**Правило:** отображение рисует рамку только если `OverlayPacket.frame_sequence == FramePacket.sequence`. Рамка без совпадающего номера не рисуется. Это устраняет геометрическую ложь: старая рамка не может оказаться на новом кадре.

## 5. Как будет работать быстрое сопровождение

Полный поиск на всех фрагментах остаётся медленным: по измерениям это до секунды. Архитектура не будет скрывать этот факт.

После того как YOLO подтвердила объект на кадре `N`, отдельный поток сопровождения:

1. берёт её рамку и уменьшенные серые кадры из кольцевого буфера;
2. последовательно переносит положение от `N` к новому кадру оптическим потоком только внутри области рамки с запасом;
3. публикует рамку для каждого конкретного кадра;
4. немедленно очищает сопровождение, если точек недостаточно, объект вышел за границу или проверка YOLO отвергла цель.

Это не поиск «похожего объекта» и не автоматическая замена цели. Новый объект может появиться только как новый результат YOLO, а не как догадка трекера. Команд управления дроном этот контур не отправляет.

Пока трекер не реализован и не подтверждён тестами, безопасный режим показывает либо рамку на исходном кадре, либо не показывает её вовсе. Он не рисует старую рамку на новом видео.

## 6. Режимы работы нового конвейера

| Режим | YOLO | Сопровождение | Назначение |
|---|---|---|---|
| `baseline` | Полный или плиточный поиск | Нет | Контрольная точка: замер точности и фактической задержки. |
| `track_after_detect` | Полный поиск для подтверждения, затем ROI вокруг подтверждённой цели | Да | Основной рабочий режим для плавной рамки. |
| `motion_hint` | Не меняет решение YOLO | Только подсказка планировщику | Отдельный эксперимент после стабильного `track_after_detect`. |

`motion_hint` не включается по умолчанию. Движение земли, камеры, листвы и бликов не доказывает наличие дрона.

## 7. Конфигурация

Параметры настольного конвейера будут находиться только в одном профиле живого запуска. До миграции текущие три JSON не удаляются и не переписываются.

Для нового профиля нужны следующие группы:

- `capture`: устройство, ширина, высота, FPS, буфер драйвера;
- `detector`: модель, порог, размер плиток, перекрытие, число потоков ONNX;
- `scheduler`: число ожидающих кадров `1`, частота полного поиска, правила ROI;
- `tracking`: уменьшение кадра, запас области, минимальное число точек, максимальный возраст;
- `display`: размер окна, масштабирование, цвета, геометрия рамки, панель CPU/TEMP/CONF/THR;
- `diagnostics`: период журнала и включение измерения таймингов.

Параметры оформления остаются в JSON, как просил владелец. `lcam` после завершения миграции остаётся одной командой без меню.

## 8. Реализованный первый этап V2

Команда `./lcam` напрямую запускает сохранённый профиль `sky`, а `./lcam --m`
открывает меню его параметров. Этот путь использует только desktop USB-захват
и окно OpenCV; UART, J7, OSD и видеопередатчик не открываются.

Поток камеры присваивает каждому кадру номер и монотонную временную метку.
Отдельный поток YOLO получает не более одного ожидающего задания: новое заменяет
старое. Результат сохраняет ссылку и номер исходного кадра. Основная картинка
и отдельная вставка берутся из одного свежего кадра потока; вставка обновляется
на каждом выводе, не ожидая следующего ответа YOLO.

Для плавного живого оверлея добавлен `src/display_tracker.py`: он переносит
подтверждённые рамки по серым кадрам камеры в исходном разрешении через Lucas–Kanade между
ответами YOLO. Трекер не распознаёт объект и не меняет порог; при разрыве кадров,
потере признаков или превышении возраста он убирает рамку, а не угадывает её.
Новый результат YOLO заново привязывает рамку. Основной экран V2 теперь может
показывать живой кадр с переносимой рамкой; вставка теперь тоже показывает
живой кадр, а не редкий сохранённый кадр инференса.

`R` включает/выключает распознавание, `Q` или `Esc` закрывает окно. Журнал сохраняется в
`test_samples/video_trials/logs/live_pipeline_v2_*.log`; раз в секунду он
показывает FPS вывода, номер текущего и обработанного кадра, уверенность,
количество рамок, ожидание worker, время YOLO и возраст результата.

В выводе задано до 60 FPS настройкой `pipeline_v2.display_fps`; фактическая
скорость зависит от захвата, окна и компьютера. Диагностическая миниатюра
строится только при приходе нового результата YOLO, а не на каждом экранном
кадре. Число потоков ONNX и частота YOLO не изменялись.

Настройки V2 расположены в `profiles.sky.pipeline_v2` внутри
`config/live_drone_profiles.json`; исходная секция `two_stage` этим режимом не
читается. Базовые проверки выполняются без открытия камеры:

```bash
./.venv/bin/python -m unittest discover -s tests -p 'test_live_pipeline*.py' -v
```

До реального запуска владелец должен подключить видеопоток и проверить картинку.
Этот этап не является завершённым алгоритмом сопровождения: перенос рамки между
кадрами будет добавлен после проверки baseline.

## 9. Этапы работ

1. **Аудит причины рассинхрона** — выполнен. Зафиксировано несоответствие кадрового номера результата YOLO текущему кадру окна.
2. **Ядро `src/live_pipeline.py`** — реализовано: пакеты кадров, ограниченная история и mailbox на один ожидающий запрос.
3. **Синтетические проверки временной целостности** — реализованы и пройдены.
4. **Базовый запуск `./lcam` и меню `./lcam --m`** — подключены. Автоматические проверки пройдены; требуется визуальная проверка владельцем на живом USB-потоке.
5. **Оптический перенос рамки в V2** — прототип добавлен; синтетическая проверка
   подтверждает перенос рамки и сброс при разрыве кадров, но нужна проверка на
   живом USB-потоке.
6. **Стандартный запуск без меню** — выполнен: `./lcam` использует сохранённый профиль; редактор вызывается отдельно через `./lcam --m`.

## 10. Критерии приёмки

Новая версия не считается рабочей, пока не выполнены все пункты:

1. Юнит-тест доказывает совпадение `frame_sequence` рамки и видео.
2. При задержке YOLO старые задания сбрасываются, а память не растёт очередью.
3. GUI продолжает показывать живое видео, но без геометрически устаревшей рамки.
4. В логе присутствуют раздельные времена: захват, ожидание, YOLO, сопровождение, возраст результата и FPS вывода.
5. Профиль не включает эксперимент поиска движения без отдельного решения.
6. Визуальный тест на USB-потоке подтверждает: рамка не остаётся на месте, где объекта уже нет, и не перескакивает на другой объект.

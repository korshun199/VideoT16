# Технические заметки переноса WinT16

## Сборка и обновления двух испытательных компьютеров

Каждый запуск `build_windows.ps1` создаёт новый каталог в `dist/`, отдельный
неподписанный архив обновления и офлайн-установщик `Install-<версия>.exe`.
Старые сборки не перезаписываются. Сборку следует
запускать в каталоге исходников на Windows, а не в каталоге установленной программы.
Параметр `-BuildPython` позволяет использовать уже подготовленное окружение сборки.

В первоначальном комплекте `Run.exe` запускает выбранную версию из `versions/`,
`Update.exe` предлагает выбрать ZIP и устанавливает новую версию рядом с прежней.
Перед переключением проверяется подпись Ed25519 владельца, состав архива и SHA-256 каждого файла. Если проверка
не прошла, прежняя версия остаётся выбранной. Предыдущая версия сохраняется на диске;
автоматическая очистка пока не предусмотрена. Подпись подтверждает, что архив выпущен
владельцем закрытого ключа; сама по себе она не подтверждает его паспортные данные.
`auth.dat`, `device.key`, `init.dat`, настройки, модель и журналы находятся
в корне программы и архивом обновления не заменяются. Для новой модели и настроек
владелец отдельно передаёт два файла. Повторная активация при обновлении не нужна.

После успешного ввода кода активации распознавание запускается сразу. Видеозахват
пытается открыть найденный оцифровщик через DirectShow и затем Media Foundation.
Работа конкретного устройства и установка на чистой Windows требуют живой проверки.
`build_update.ps1` собирает неподписанный ZIP новой версии в `dist/`, не пересобирая
запускатель и окно обновления. На Linux команда `./.venv/bin/python WinT16/build.py`
отправляет только исходники на сборочный Windows-компьютер, забирает архив и подписывает
его локальным ключом владельца. В результате в `WinT16/dist/` появляется готовый ZIP.
Закрытый ключ подписи остаётся только на Linux. Производный AES-ключ модели
передаётся сборщику по SSH во временном исходном архиве, встраивается в Engine.exe,
а временный каталог конкретной сборки удаляется после получения результата.
Адрес сборочной машины и путь к SSH-ключу находятся в игнорируемом `build.local.json`.
Неподписанный архив клиент не принимает. Повторный запуск одной установки Windows блокируется
системным мьютексом: одновременно открыть одну установку дважды нельзя. Это важно для
USB-оцифровщиков, у которых второй backend может нарушить работающий поток.

## Первый срез: платформенный слой

`Run.exe` сразу запускает распознавание; пользовательского окна настроек нет.
Источник по умолчанию — `auto_hdmi`: Windows перечисляет видеоустройства по
имени и USB VID/PID, выбирает ровно одно совпадение с фильтрами из
`settings.json` и открывает его через DirectShow или Media Foundation. Если
оцифровщик подключат позже, программа остаётся запущенной и повторяет поиск.
Встроенная камера не выбирается по индексу и не используется как запасной
вариант. При нуле или нескольких совпадениях программа ждёт, не угадывая.
Зависимость `cv2-enumerate-cameras` нужна для получения имён устройств.

`runtime/metrics.py` получает загрузку CPU через `psutil`. Температура
показывается только тогда, когда ОС или драйвер предоставляют датчик с CPU-
меткой; чужая температура (например, GPU) не подменяет температуру процессора.
Внизу окна по центру стоят внешний `logo.png` и версия из `settings.json`.

`WinT16/settings.json` остаётся внешним заменяемым файлом. Клиенту отправляются
ровно два файла обновления: общая зашифрованная модель `.v16m` и новый
`settings.json`; персональный `auth.dat` остаётся на компьютере пользователя.
Обычный `.onnx` разрешён только при запуске исходников; собранный `Run.exe`
отказывает в нём. Модель расшифровывается только в RAM после проверки
аппаратного отпечатка и проверки короткого кода. Это барьер от обычного копирования,
не абсолютная защита от анализа запущенного процесса.
`model_path` разрешается относительно каталога `settings.json` (по умолчанию
`WinT16/models/...`), поэтому замена модели/настроек в дальнейшем не потребует
пересборки `Run.exe`. Зависимости перечислены в `WinT16/requirements.txt`;
автономный установщик ещё не собран.

Формат `.v16m` — AES-GCM. Новая активация использует AES-128;
старый AES-256 контейнер оставлен для прежних тестовых сборок. Общий
32-байтовый ключ владельца хранится в закрытом каталоге `owner_keys`, а AES-128
ключ модели встраивается в собранную программу. Это позволяет выдавать короткий
ответный код, но не защищает модель от человека, умеющего анализировать EXE.
Такое упрощение намеренное: цель — не дать запустить обычную копию каталога на
чужом ноутбуке, а не построить профессиональную DRM.

При отсутствии подходящего `auth.dat` приложение показывает окно активации.
В первом крупном поле отображается ровно 12 заглавных символов из набора
`0–9`, `A–Z` без `I`, `L`, `O`, `U`, чтобы меньше путать их при диктовке. Код
вычислен из SHA-256 отпечатка оборудования. Его можно скопировать кнопкой
или выделить мышкой, продиктовать владельцу, а в нижнее поле ввести 12-значный
ответ. Допускаются пробелы/дефисы; ввод автоматически показывается заглавными.
Программа проверяет ответ офлайн и создаёт `auth.dat`; отдельные файлы выбирать
не нужно. Сырые серийные номера не передаются. Уже выданные 32-символьные
активации v2 продолжают работать.

Владелец выпускает ответ командой (запрос можно передать аргументом или вставить
после приглашения):

```bash
python3 WinT16/tools/issue_activation.py '0123456789AB'
```

Для новых компьютеров аргумент — код из 12 знаков; генератор отвечает 12 знаками.
32-символьный запрос оставлен для повторного выпуска кода старой версии.
Новый ответ — 60-битный HMAC от запроса с ключом модели. Этот ключ есть в EXE,
поэтому знающий Python/реверс пользователь способен воспроизвести генератор или
извлечь ключ. При замене оборудования владелец выдаёт новый ответ; прежний файл
активации сохраняется с суффиксом `previous`.

Перед первоначальной сборкой на Linux подготовить закрытый модуль ключа:

```bash
python3 WinT16/tools/prepare_build_key.py
```

Файл `WinT16/runtime/_embedded_model_key.py` игнорируется Git и содержит ключ;
его нельзя публиковать. Сборка обновления `WinT16/build.py` передаёт ключ
сборочному Windows-компьютеру по SSH во временном архиве, а затем удаляет
временный каталог этой конкретной сборки. Сам EXE, конечно, сохраняет ключ.
При обычной замене модели продолжайте пользоваться тем же `model_aes.key`;
смена этого ключа требует новой сборки движка, иначе модель не откроется.

Владелец создаёт общий зашифрованный файл модели так:

```bash
python3 WinT16/tools/encrypt_model.py trained.onnx models/Drone.v16m --short-code
```

Расшифрованный `.onnx` приложением на диск не записывается. Настройки и модель
обновляются двумя файлами; переактивация после штатного обновления не нужна.

## Ограничения текущего среза

Имя оцифровщика в `hdmi_device_name_contains` — предварительный фильтр. Если
Windows покажет его под другим именем или одновременно подключено несколько
подходящих устройств, нужно один раз уточнить фильтр или VID/PID в JSON. На
тестовой Windows 11 проверены сборка EXE, загрузка модели и обновление с сохранением
активации. Конкретный HDMI-оцифровщик, видимое окно и Windows 10 пока не проверены;
офлайн-установщик требует проверки на чистом компьютере.

## Ограничения проверки

Автотесты этого слоя используют поддельный интерфейс камеры и не доказывают,
что конкретный драйвер USB-оцифровщика откроется в Windows. Для живой проверки
нужен компьютер Windows с подключённым HDMI-оцифровщиком.
